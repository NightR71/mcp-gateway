## 一句话定位

面向海洋数据管理场景的「自然语言 → 数据问答」专项：Dify 工作流 + Python 自研 MCP Server 对接达梦数据库，让非技术人员用自然语言查数（**口述级**）。

## 痛点（口述级）

海洋数据管理场景下，业务人员查数需要写 SQL 或找开发——需要一个自然语言入口 + 护栏，保证本地小模型能力受限时流程仍可用。

## 方案（口述级，逐条）

- Dify 工作流编排数据问答流程；
- Python 自研 MCP Server 对接达梦数据库；
- 本地模型 NL2SQL，**固定查询兜底 + 默认分页 10 条**，保障小模型可用性；
- 对话护栏 Demo：BERT 违规词检测 + SQL 注入拦截；
- 独立完成数据查询流程设计、MCP 服务开发与对话护栏 Demo。

## 个人贡献（口述级）

独立完成上述专项的设计与交付；Demo 完成目标运行。

## 结果（口述级）

Demo 完成目标运行；本地小模型能力受限，以固定查询兜底保障流程可用。

## 追问预案

### L1（确认层）
- **做了什么**：按方案四条口径简述（工作流 / MCP Server / NL2SQL 兜底 / 护栏），落点"专项交付、时间短、Demo 达成目标"。
- **为什么有固定查询兜底**：本地小模型 NL2SQL 输出不稳定，高频问题走固定查询保证可用性，长尾走模型生成——先保可用，再谈智能。

### L2（深挖层）
- **护栏怎么设计**：违规词检测（BERT）+ SQL 注入拦截做在入口；NL2SQL 侧只读语义（与网关 demo_sql 的只读校验思路一致：仅 SELECT/WITH、危险关键字拦截、分页截断）。
- **为什么用 Dify + 自研 MCP Server**：Dify 快速编排流程，自研 MCP Server 让工具接入标准化——这段经历是后来"工具层→基础设施层"主线的中间一环。

### L3（挑战层）
- **深挖具体表结构 / 数据量 / 指标**：**素材待补，不编造**。固定回应方向：「这段实习是短期专项，Demo 性质，我掌握的细节以流程设计为主；具体数据环境不便展开。同类问题在我开源的网关项目里有完整可验证实现（NL2SQL 双引擎 + 只读校验），可以看那边。」
- **「做了性能优化吗？」**：不做任何性能/大数据量主张（红线）；如实回答专项未涉及，可谈"知道怎么做"的通用思路（只读校验、分页截断）。
