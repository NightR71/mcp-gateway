# MCP Gateway 项目开发全过程说明

> 这是一份给非开发人员阅读的项目说明。它不只解释“项目有什么功能”，也记录了项目为什么这样设计、每一步怎样落地、遇到了什么真实问题，以及个人如何与 AI 分工完成开发。
>
> 依据：本仓库的规划文档、实际代码、测试目录、部署记录和 Git 提交记录（截至 2026-08-25）。

## 1. 先用一句话理解项目

这个项目可以理解成一个“AI 工具总管”：

- 外面的 AI 或业务系统只需要记住一个地址：MCP Gateway。
- Gateway 负责身份验证、限流、工具搜索、调用记录和错误处理。
- 真正干活的工具可以来自很多 MCP Server，例如数据库、内部 API 或其他自动化服务。
- 本项目用一个“迷你电商数据库”作为演示，让用户用中文提问，系统自动查询数据并返回结果。

例如，用户问“有多少客户？”：

```text
用户/AI
  ↓ 只访问 Gateway
Gateway 验证 API Key、检查限流、找到 demo_sql__ask
  ↓ MCP 协议
demo_sql_server 生成只读 SQL 并查询 SQLite
  ↓
Gateway 把结果交还给用户/AI
```

这样做的价值是：以后增加新的工具时，调用方不用分别学习每个工具的地址、认证方式和协议，只需要继续使用 Gateway。

## 2. 为什么选择这个题目

项目不是简单做一个“问数据库”的页面，而是围绕企业真实场景设计：

1. **工具越来越多时怎么管理？**  
   如果把所有工具都塞给 AI，会浪费上下文、增加 token 成本，也会降低 AI 选对工具的概率。
2. **不同调用方怎么隔离？**  
   一个客户应该只能看到和调用自己被授权的工具。
3. **下游服务出故障怎么办？**  
   某个 MCP Server 停机，不应该让整个 Gateway 一起失效。
4. **AI 结果如何让用户看懂？**  
   用户不仅要看到最终答案，也应该能看到用了哪个工具、耗时多久、是否发生错误。
5. **本地、Docker、Serverless 能否使用同一套代码？**  
   开发环境适合用本地子进程，云平台却可能禁止拉子进程，因此必须提前抽象传输方式。

因此，项目的主线从“把协议接通”逐步升级为：

> 多工具接入 → 统一 API → 安全与可观测 → 工具路由 → 网关内 Agent → 可视化工作台 → 流式体验 → 权限与可靠性。

## 3. 我与 AI 的分工方式

这里的 AI 不是替代思考，而是被当作一个可以反复校验的开发搭档。

### 3.1 我负责的部分：目标、边界和验收

我先确定项目要解决的业务问题，再把大目标拆成可以验收的阶段。每个阶段都要求同时满足四件事：

- 代码完成；
- 对应测试通过；
- 启动后可以实际运行；
- 旧接口和旧示例不能被破坏。

我还负责做取舍。例如二阶段没有直接上 Redis、向量数据库、Kubernetes 或前端框架，而是先用零依赖关键词路由、SQLite、原生 JavaScript 和 Mock 模型把完整闭环跑通。这样既控制范围，也保证面试时能讲清楚每个设计决定。

### 3.2 AI 负责的部分：实现、检查和重复劳动

我把每个阶段拆成明确任务交给 AI：

- 根据接口契约生成模块和类型；
- 根据现有代码补充测试；
- 阅读 MCP SDK 的实际 API，适配传输层；
- 运行 `pytest`、`ruff` 和集成测试；
- 根据失败信息定位是代码问题还是环境问题；
- 生成文档初稿，再由我核对是否与代码事实一致。

AI 的输出不直接视为正确答案。每次修改后都要通过测试、实际请求或部署验收；遇到 AI 误判时，保留错误原因并调整下一步提示词。这种“人定方向、AI 加速实现、测试负责裁判”的方式，比一次性让 AI 生成整个项目更可靠。

## 4. 整体结构：每个文件夹负责什么

```text
app/
├── main.py                 启动 FastAPI，组装所有模块
├── config.py               读取默认值、YAML 和环境变量
├── core/
│   ├── security.py         API Key 存储与查询
│   ├── rate_limit.py       令牌桶限流
│   ├── logging.py          结构化日志
│   └── metrics.py          Prometheus 指标
├── mcp/
│   ├── transports.py       stdio、SSE、HTTP 传输工厂
│   ├── client.py           MCP 客户端和进程内客户端
│   ├── registry.py         工具注册、命名空间、调用和自愈
│   ├── schemas.py          Gateway 自己的稳定数据模型
│   └── tool_router.py      根据问题筛选相关工具
├── api/
│   ├── deps.py             统一依赖注入、鉴权和限流顺序
│   └── routes/             health、tools、servers、agent 接口
├── agent/
│   ├── models.py           OpenAI 兼容模型和 Mock 模型
│   ├── runner.py           Agent 循环
│   └── schemas.py          Agent 请求、步骤和响应
├── schemas/                通用请求响应模型
└── ui/                     不需要构建工具的浏览器工作台

servers/demo_sql_server/
├── server.py               MCP Server，提供 4 个工具
├── db.py                   SQLite 表结构、种子数据和只读校验
├── nl2sql.py               规则引擎、双引擎工厂
└── llm_translator.py       可选的 OpenAI 兼容 LLM 翻译器
```

这里最重要的分层原则是：路由只负责接收参数和组装响应；MCP 协议细节只放在 `app/mcp/`；配置集中在 `app/config.py`；业务逻辑不散落在接口函数里。

## 5. 从零搭建的实际过程

### 阶段 0：先搭工程骨架，而不是一开始堆功能

第一步先建立 Python 3.12、FastAPI、MCP SDK、pytest、ruff、Docker 和 GitHub Actions 基础。入口是 `app/main.py`，最先实现：

- `/health`：确认服务是否活着；
- `/metrics`：让 Prometheus 能采集指标；
- YAML + 环境变量配置；
- structlog 结构化日志；
- CI 自动执行 lint 和测试。

**为什么先做这些？**  
因为如果没有健康检查、测试和统一配置，后面即使功能能跑，也很难知道是代码错了、环境错了还是部署错了。

**实际设计：** 配置优先级为“代码默认值 < YAML < 环境变量”。例如端口可以写在 YAML 中，也可以用 `GATEWAY_PORT=9000` 临时覆盖；敏感 Key 不写进代码。

### 阶段 1：打通第一个 MCP Server

先做最小的 `echo` 工具，目标不是业务复杂，而是验证完整链路：

```text
Gateway → MCP Client → stdio 子进程 → demo_sql_server → 返回结果
```

随后实现 `MCPClient`，用 `AsyncExitStack` 管理连接生命周期。连接时完成 MCP 初始化握手，关闭时按逆序释放会话、传输和子进程。

为了支持不同部署环境，把连接方式集中到 `transports.py`：

- **stdio**：Gateway 拉起本地 Python 子进程；
- **SSE**：连接远程 SSE Server；
- **Streamable HTTP**：通过 HTTP 连接独立容器中的 Server；
- **inprocess**：不拉子进程，直接在当前 Python 进程中加载 MCPServer。

`registry.py` 是这一阶段的核心。它启动时并发连接所有启用的 Server，并把工具统一登记为：

```text
{server}__{tool}
例如：demo_sql__ask
```

双下划线不是随便选的：它既能区分来源，又符合 OpenAI function calling 对工具名称的限制。

如果某个 Server 连接失败，注册中心不会阻塞其他 Server；失败状态会记录下来，后续阶段再加入自动重连。

### 阶段 2：把工具变成统一 REST API

MCP 是 Gateway 内部与 Server 对话的协议，但外面的客户端不应该被迫理解 MCP 细节，所以增加稳定的 REST 接口：

| 接口 | 用途 |
|---|---|
| `GET /health` | 健康检查 |
| `GET /tools` | 查看当前可用工具 |
| `POST /tools/{tool_name}/call` | 调用指定工具 |
| `GET /servers` | 查看 Server 连接状态 |
| `GET /metrics` | 查看 HTTP 和工具调用指标 |

工具调用的请求示例：

```json
{
  "arguments": {
    "question": "有多少客户？"
  }
}
```

返回内容统一成 Gateway 自己的 `ToolCallResult`，上层不直接依赖 MCP SDK 类型。这样以后替换 SDK 或增加其他下游协议时，API 不需要跟着改变。

### 阶段 3：加入鉴权、限流和可观测性

#### API Key 鉴权

客户端在 `X-API-Key` 请求头中携带 Key。`deps.py` 统一规定顺序：

1. 没有 Key 或 Key 不存在：返回 401；
2. Key 正确但超过额度：返回 429；
3. 通过后才进入具体业务。

Key 由 `APIKeyStore` Protocol 抽象，当前实现是 SQLite。数据库访问用 `asyncio.to_thread` 包装，避免同步 SQLite 操作阻塞事件循环。初始化会建表并写入 YAML 中的演示 Key，重复启动不会重复覆盖。

#### 令牌桶限流

每个 Key 有独立的桶，容量就是每分钟额度。令牌按“额度 ÷ 60”每秒补充，请求消耗一个令牌；没有令牌时返回 429 和 `Retry-After`。

这是一个适合 MVP 的单进程实现：简单、可解释、容易测试。它还不是多实例生产方案，生产环境应换成 Redis 等共享存储。

#### 日志和指标

日志使用 structlog，事件名称例如 `mcp_server_connected`、`tool_call_failed`，便于机器检索。

Prometheus 记录：

- `mcp_gateway_tool_calls_total`：每个工具成功、下游错误或异常的次数；
- `mcp_gateway_tool_call_duration_seconds`：工具调用耗时；
- FastAPI 请求数和 HTTP 延迟。

指标通过 `ToolCallTimer` 在调用成功、返回错误和抛异常三种路径都记录，不吞掉原始异常。

### 阶段 4：做出可演示的 demo_sql_server

为了让项目不是“只有接口”，增加迷你电商数据库：

- `customers`：客户、城市、会员等级；
- `products`：产品、品类、价格、库存；
- `orders`：客户、产品、数量、金额、状态和下单时间。

Server 提供 4 个工具：

1. `ask`：中文问题转 SQL、执行并返回 Markdown 表格；
2. `run_sql`：直接执行只读 SQL；
3. `list_tables`：查看表结构；
4. `echo`：链路调试。

第一版 NL2SQL 采用 13 条规则模板。比如“总销售额”会匹配到 `SUM(amount)`，“库存不足”会按库存排序。它不是为了假装成通用大模型，而是为了让离线演示确定、稳定、可复现。

数据库层有两道保护：

- 只允许以 `SELECT` 或 `WITH` 开头；
- 拒绝多条语句和 `INSERT`、`UPDATE`、`DELETE`、`DROP` 等危险关键字；
- 查询最多返回 50 行，避免一次响应过大。

### 阶段 5：Docker 和公网部署

本地配置让 Gateway 用 stdio 拉起 demo Server；Docker 配置则把两者拆成两个容器：

```text
gateway 容器 --Streamable HTTP--> demo_sql 容器
```

`docker-compose.yml` 中 Gateway 要等待 demo_sql 的 healthcheck 通过后再启动，减少“Gateway 已启动但下游还没准备好”的问题。

Vercel 是一次真实的兼容性考验。最初仍使用 stdio 子进程，但线上子进程看不到构建阶段安装的 `mcp`，导致工具注册数量为 0。排查后没有破坏本地和 Docker 方案，而是增加 Vercel 专用配置：

- 使用 `inprocess` 在同一个 Python 进程加载 `servers.demo_sql_server.server`；
- SQLite 写入 `/tmp`；
- 保留本地 stdio 和 Docker HTTP 两套原有配置。

这体现了“抽象传输，而不是把某个平台特殊逻辑硬塞进路由”的设计价值。

线上记录中已验证 `/health`、带 Key 的 `/tools`、`/servers`、`/ui`、`POST /agent/run` 和工具 SSE 接口。需要如实说明：Vercel 在中国大陆存在 DNS 污染，演示链接可能无法直接访问；这是网络环境限制，不是应用代码错误。

### 阶段 6：二阶段重新评估

一阶段完成后，没有直接继续加零散功能，而是先重新检查“文档声称完成、代码实际存在、测试实际验证”是否一致。评估结论是：

- MCP 接入、统一 API、鉴权、限流、日志、指标、Docker 和 Vercel 已有基础；
- 但 AI 逻辑主要在 `examples/`，网关本身还不是 Agent；
- 工具数量增长后没有工具路由；
- 没有 UI、流式输出、最小权限和断线自愈。

所以二阶段按硬依赖严格执行 `0 → 1 → 2 → 3 → 4`，再按单人开发建议执行 `5 → 6 → 7`，没有把路线无限扩大。

## 6. 二阶段的完整升级

### 6.1 Semantic Tool Routing：先筛选再交给 AI

`tool_router.py` 是零外部依赖的 v1 路由器：

- 英文和数字按 token 切分；
- 中文按 2-gram 切分，例如“销售额”拆成“销售”和“售额”；
- 工具名权重 3，描述权重 2，参数 Schema 权重 1；
- 根据命中覆盖率排序；
- 工具很少时不筛选，避免小项目行为改变；
- 没命中时返回前几个工具作为保底。

因此可以调用：

```text
GET /tools?query=销售额&top_k=2
```

Agent 也只注入相关工具，而不是把所有工具塞进模型上下文。未来可以把 `Scorer` Protocol 替换成 embedding 实现，但本阶段刻意不引入向量库。

### 6.2 AgentRunner：把 Agent 放进网关

`app/agent/runner.py` 把一次任务拆成可观察步骤：

```text
用户问题
→ 工具选择
→ 模型提出工具调用
→ Gateway 执行工具
→ 结果回填模型
→ 最终回答
```

网关内 Agent 直接调用 `registry.call_tool()`，不通过 HTTP 回环调用自己，减少一层网络开销。

`Model` Protocol 让模型实现可替换：

- 真实模式：调用 OpenAI 兼容的 `chat/completions`，因此也可以接 One-API、Ollama 或 DeepSeek 等兼容端点；
- Mock 模式：第一轮固定调用 `demo_sql__ask`，第二轮把工具结果包装成答案，不需要 Key，适合离线演示和自动化测试。

新增：

```text
POST /agent/run
```

返回 `answer`、`steps`、工具总数、实际注入数量和往返轮数。Agent 没启用时返回明确的 503，而不是假装成功。

### 6.3 Interactive Agent Workbench：让过程看得见

工作台由 `index.html`、`app.js`、`style.css` 组成，不使用 React、CDN 或前端构建链。FastAPI 直接把它挂在 `/ui`，根路径 `/` 重定向到 `/ui`。

页面可以：

- 输入 API Key 和中文问题；
- 查看 User、Agent、Gateway、Tool Result 等时间线卡片；
- 看到工具名和耗时；
- 点击健康检查和列出工具；
- 直接看到 401、429、503 等错误文案。

Key 只存在输入框和请求头，不写入 `localStorage`。这不是完整后台系统，而是一个聚焦“展示完整调用链”的演示工作台。

### 6.4 Streaming：把等待变成实时反馈

新增两个 SSE 接口：

- `POST /agent/run/stream`：`step → token* → step(final) → done`；
- `POST /tools/{name}/call/stream`：`start → result → done`。

Agent 的最终回答会逐字产生，浏览器通过 `response.body.getReader()` 按空行拆分 SSE 帧，再把 token 追加到最终回答卡片。

这里有一个明确边界：本阶段只做 HTTP 层 SSE，没有把 MCP 协议内部的 progress 通知继续透传。因为当前示例工具是瞬时 SQL，投入复杂协议改造的收益较低，先保证公开 API 稳定。

### 6.5 NL2SQL 双引擎：稳定性和 AI 能力兼得

在规则引擎之上新增 `LLMTranslator`，支持 OpenAI 兼容端点。系统有三种模式：

- `rule`：只使用规则；
- `llm`：使用 LLM；
- `hybrid`：规则命中优先，未命中才调用 LLM。

`hybrid` 是实际项目中比较重要的折中：常见问题走确定性路径，复杂问题才消耗模型；LLM 没配好时自动退回规则模式，旧行为不改变。系统提示词要求模型只能生成只读 SQL，并把数据库结构传给模型。

所有 LLM Key 只从 `DEMO_SQL_LLM_API_KEY` 读取，绝不写入 YAML。结果会标注“引擎：规则”或“引擎：LLM”，方便排查和演示。

### 6.6 最小多租户和工具白名单

没有直接实现复杂 RBAC，而是先完成最短可用路径：

- Key 增加 `tenant`；
- Key 增加 `allowed_tools`；
- `None` 表示兼容旧数据，允许全部工具；
- 白名单 Key 只能在 `/tools` 看到被授权工具；
- 真实存在但未授权的工具返回 403；
- 根本不存在的工具仍返回 404。

SQLite 启动时会用 `PRAGMA table_info` 检查旧表，缺少 `tenant` 或 `allowed_tools` 就执行幂等 `ALTER TABLE`。这避免了升级时要求用户手动删库重建。

演示配置中：

- `dev-key-please-change` 可以访问全部 4 个工具；
- `limited-tools-key` 只能访问 `demo_sql__ask`。

### 6.7 可靠性：断线自愈、总超时和错误分类

最后一阶段解决“下游挂了怎么办”：

1. 启动时多个 Server 并发连接，单点失败不阻塞整体；
2. 失败 Server 被记录在 `FailureState`；
3. 后台任务按指数退避重试，间隔从 2 秒开始，最多 60 秒；
4. 连接类调用异常会摘除该 Server 的客户端和工具；
5. 重连成功后自动重新注册工具；
6. 工具调用受 `tool_call_timeout` 总时长保护，超时返回明确 502。

过程中发现一个真实难题：MCP SDK 2.x 会把对端关闭包装成带错误码的 `MCPError`，并不一定是 Python 的 `ConnectionError`。如果只判断传统异常类型，断线自愈会漏判。最终 `classify_error()` 同时识别 SDK 的连接关闭码 `-32000` 和请求超时码 `-32001`，再决定是重连、返回超时，还是保留为普通工具错误。

## 7. 一次完整请求到底经过哪些步骤

以工作台提问“有多少客户？”为例：

1. 浏览器调用 `POST /agent/run/stream`，在 Header 放入 `X-API-Key`；
2. 依赖注入先查 Key，失败返回 401；
3. 令牌桶消耗一个令牌，超限返回 429；
4. AgentRunner 从 Registry 取得工具；
5. ToolRouter 根据问题筛选候选工具；
6. Mock 或真实模型决定调用 `demo_sql__ask`；
7. Registry 按命名空间找到 `demo_sql_server` 的原始工具 `ask`；
8. MCP Client 通过当前传输方式执行工具；
9. `demo_sql_server` 惰性初始化 SQLite，规则引擎生成：

   ```sql
   SELECT COUNT(*) AS 客户总数 FROM customers
   ```

10. 数据库只读校验通过，返回结果 `5`；
11. 工具结果回填模型；
12. Agent 生成最终回答；
13. SSE 把步骤、逐字回答和完整响应实时发给浏览器；
14. Prometheus 同时记录工具次数、状态和耗时，structlog 记录过程事件。

这就是面试时可以用一句话描述的“从用户问题到数据库结果的完整闭环”。

## 8. 真实遇到的难题与解决方法

### 难题一：MCP SDK 版本和文档示例不一致

实际环境使用 MCP SDK 2.0.0，`streamable_http_client` 返回的是二元组，服务端类路径是 `mcp.server.mcpserver.MCPServer`，与旧示例并不完全一致。

**解决：** 以已安装 SDK 的实际 API 和测试结果为准，先用最小 transport 测试验证，再扩展注册中心；不盲目照搬旧教程。

### 难题二：Vercel 子进程能启动但加载不到依赖

线上曾出现 `ModuleNotFoundError: No module named 'mcp'`，最终表现为工具注册数为 0。

**解决：** 增加 `InProcessClient`，在网关进程内导入 MCPServer，共用同一份依赖；Vercel 使用 `gateway.vercel.yaml`，本地和 Docker 不变。

### 难题三：环境权限问题容易伪装成代码问题

记录中遇到过 DSH 沙箱拦截文件写入和 stdio 子进程、Windows 安全软件拦截 pytest 子进程、pyenv shim 抢占 PATH、uv 缓存损坏等问题。

**解决：** 先区分“代码失败”和“环境失败”：使用 `uv run`、临时 `UV_CACHE_DIR`、inprocess/fake client 测试，并用 GitHub Actions 或真实部署环境复验。不能因为本地沙箱报错就贸然改业务代码。

### 难题四：SSE 是否会被平台缓冲

流式接口在理论上可能被 Serverless 平台缓冲，导致浏览器最后一次性收到内容。

**解决：** 不停留在理论判断，实际用 HTTP 验证事件序列。线上工具 SSE 已验证 `start → result → done`，Agent SSE 也能收到连续 step 和 token。

### 难题五：如何增加权限又不破坏旧客户端

如果把旧接口返回结构改掉，examples、CI 和已有使用方都会受影响。

**解决：** 使用增量扩展：保留原来的 `/tools`、`/tools/{name}/call` 和响应模型，只增加可选 query、stream 端点、403 分支和新的状态字段；旧 Key 没有白名单时仍按全量处理。

### 难题六：LLM 不稳定时演示不能失效

真实模型可能没 Key、超时或返回格式异常。

**解决：** `MockModel` 保证离线闭环，NL2SQL 用规则优先和自动降级，所有外部 Key 从环境变量读取。这样“AI 能力”与“演示可用性”不会互相绑死。

## 9. 测试和质量控制

测试目录按模块对应组织，覆盖：

- 配置和健康检查；
- stdio、HTTP、SSE、inprocess 传输；
- Registry 注册、失败恢复和重连；
- Tool Router 分词、排序、top-k 和保底；
- Agent 同步、流式、直接回答和最大轮数；
- 鉴权、429 限流、403 白名单、404 未知工具；
- SQLite 只读 SQL 和 NL2SQL；
- OpenAI/LangChain 示例。

每个受保护接口至少考虑成功、401、429；新增能力再覆盖 403、404、502、503。阶段完成前执行：

```bash
uv run pytest
uv run ruff check .
uv run ruff format --check .
```

GitHub Actions 在 push 和 Pull Request 时执行 `uv sync --locked`、Ruff 和 pytest，避免“本地能跑、合并后失败”。

需要如实区分两类结果：项目记录中本机历史验证曾达到全量通过；某些沙箱运行出现的失败主要来自子进程和文件权限拦截，不能直接当作代码缺陷。最终仍通过本机、CI、Docker 或线上验收交叉确认。

## 11. 当前边界：不把 MVP 包装成生产成品

当前项目已经是一个完整、可部署、可测试的工程化演示，但仍有明确限制：

- API Key 在演示配置中是明文，生产应使用密钥管理或哈希存储；
- 限流桶是单进程内存态，多实例不共享；
- SQLite 和 `/tmp` 状态不适合生产持久化；
- `/metrics` 当前不需要 Key，生产可能需要保护；
- 还没有完整 RBAC、审批流、后台管理、计费和模型路由；
- 还没有 Redis 分布式限流、OpenTelemetry 和 Kubernetes；
- Tool Router 当前是关键词方案，不是 embedding 语义检索；
- SSE 做的是 HTTP 层事件，不是完整 MCP progress 透传。

这些不是遗漏后假装不存在，而是主动划定范围。下一步可以在不推翻现有分层的前提下替换存储、路由打分器和部署组件。

## 12. 面试时的简洁总结

我先把 MCP Gateway 拆成配置、协议、业务接口和横切能力四层，先用 echo 工具验证最小链路，再逐步增加注册中心、统一 REST API、API Key、令牌桶、日志和 Prometheus。  
完成基础闭环后，我重新评估发现 AI 逻辑还停留在示例脚本、工具多了会造成上下文膨胀、缺少交互展示，于是按依赖关系增加本地 Tool Router、网关内 AgentRunner、原生 JS 工作台和 SSE。  
之后再补上规则优先的 LLM NL2SQL、租户和工具白名单，以及指数退避重连和总超时。开发过程中我负责业务目标、范围控制、兼容性红线和最终验收，AI 负责模块实现、测试补全和错误定位；每个阶段都用代码、测试、运行和部署四种证据确认，而不是只看“代码生成出来了”。  
最终项目既能解释 AI Agent 如何调用工具，也能说明一个企业网关如何处理安全、可观测性、部署差异和故障恢复。
